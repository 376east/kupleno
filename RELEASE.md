# Выпуск Куплено

Текущий предпросмотр для Chrome и Edge собирается из [extension/next](extension/next/). [Установка и резервное копирование](docs/PREVIEW.md#запуск).

## Проверка без публикации

Для проверки на GitHub откройте [Build and publish preview](https://github.com/376east/kupleno/actions/workflows/release-candidate.yml). После включения workflow в основную ветку нажмите **Run workflow** и выберите ветку с нужным коммитом. Результат появится в артефакте `kupleno-preview-<run_id>-<run_attempt>`.

Локально используйте Node.js 24 и Python 3.10+.

```sh
npm ci
npm --prefix extension/next ci
npx playwright install chromium
python scripts/verify-next-release.py --output-dir dist/next-release
```

Команда запускает проверку типов, тесты, чистую установку в Chromium и сценарии с тестовыми ответами магазинов. Две сборки должны дать одинаковый ZIP. Рядом сохраняются `SHA256SUMS` и `provenance.txt` с версией и SHA исходников.

## Публикация предпросмотра

После проверки конечного коммита возьмите версию из [extension/next/package.json](extension/next/package.json) и создайте аннотированный тег. Пример для `0.22.15`.

```sh
git tag -a v0.22.15-preview.1 -m "Куплено 0.22.15 preview 1"
git push origin refs/tags/v0.22.15-preview.1
```

Новый тег запускает ту же проверку и публикацию GitHub prerelease с `kupleno-extension.zip`, `SHA256SUMS` и `provenance.txt`. Событие обновления или удаления тега пропускается. Для повторной публикации после исправления нужен новый тег с увеличенным номером предпросмотра. Если публикация оставила черновик, проверьте состояние тега и файлов перед ручным завершением черновика.

## Что считается выпуском

Есть три разных результата:

1. обычная локальная или CI-сборка из текущих исходников;
2. проверенный кандидат из чистого точного аннотированного тега;
3. опубликованный GitHub Release.

Только третий результат доступен обычному пользователю как релиз. Новый аннотированный тег автоматически проходит полную проверку и публикуется в GitHub Release. Подпись и магазины расширений остаются отдельным решением.

Единственный источник архива — явный список `runtime_files` в `scripts/package-extension.sh`. Архив `kupleno-extension.zip` в корне запрещён; результат всегда находится в `dist/`.

## Требования

- Node.js из `.nvmrc` и зависимости из зафиксированного `package-lock.json`;
- `npm`, `git`, `zip`, `unzip` и `shasum`;
- чистый `main`, прошедший все три задания [CI](.github/workflows/ci.yml), включая Semgrep CE;
- живой Chromium 116+ с тестовыми входами в поддерживаемые маркетплейсы;
- аннотированный тег `vX.Y.Z`, точно соответствующий версии.

## Подготовка

1. Сначала завершить код, документацию и review, затем заморозить diff.
2. Сверить версию в `extension/manifest.json`, `package.json`, README и заголовке CHANGELOG.
3. Проверить разрешения, сетевые домены, политику данных, формат backup и миграции.
4. Выполнить:

```sh
npm ci
npx playwright install chromium
npm run verify
npm run verify:reproducible
```

5. Убедиться, что автоматическая проверка открыла именно готовый ZIP и сохранила снимки в `dist/browser-smoke/`; пройти оставшийся ручной сценарий из `docs/TESTING.md`.
6. Если интерфейс изменился, визуально проверить и обновить снимки README только из этого прогона exact ZIP.
7. Для каждого маркетплейса проверить вход, непустую историю, несколько страниц при наличии, возврат, повторный запуск и честное отображение неполного результата.
8. Скачать backup, восстановить его в отдельном чистом профиле и сравнить итог, профили и настройки.

Без живого прогона сборщиков версия может быть технически корректным кандидатом, но не готовым публичным релизом.

## Неизменяемый кандидат

После коммита и успешного CI создаётся аннотированный тег:

```sh
git tag -a vX.Y.Z -m "Куплено vX.Y.Z"
git push origin vX.Y.Z
```

Push точного тега автоматически запускает workflow `Build and publish release`. Если GitHub не доставил событие push, владелец может запустить тот же workflow вручную только с `main` и передать уже существующий тег в поле `tag`. Запуск из произвольной ветки пропускается, а workflow всё равно переключается на тег и проверяет его полностью. Он повторно выполняет:

```sh
npm run verify:release -- vX.Y.Z
```

Команда завершается ошибкой, если рабочее дерево грязное, тег лёгкий, тег не указывает на точный `HEAD`, версии расходятся, CHANGELOG не обновлён или сборка невоспроизводима.

Кандидат содержит:

- `kupleno-extension.zip`;
- `SHA256SUMS`;
- `provenance.txt`;
- `release-evidence.json` с полным списком файлов.

## Публикация

После успешной проверки workflow сам формирует текст из раздела текущей версии в `CHANGELOG.md` и создаёт скрытый draft GitHub Release. В него попадают только `kupleno-extension.zip`, `SHA256SUMS`, `provenance.txt` и `release-evidence.json` из той же проверенной папки `dist/`. Релиз становится публичным и `latest` только после загрузки всех файлов; неудачный draft удаляется автоматически, а тег сохраняется. Candidate artifact остаётся для диагностики.

Если релиз с таким тегом уже существует, workflow завершается ошибкой и ничего не заменяет. Нельзя передвигать существующий тег или молча заменять asset: исправление выпускается новой patch-версией. Если менялись сборщики или не подтверждена текущая совместимость, после публикации выполняется короткий сбор из каждого маркетплейса.

## Откат

Git-тег и опубликованный asset не изменяются. При ошибке выпуск помечается проблемным, пользователю даётся понятная инструкция, а исправление выходит новой patch-версией. Для распакованной установки сохраняются предыдущий ZIP и backup; полный порядок описан в `docs/DATA_AND_COMPATIBILITY.md`.
